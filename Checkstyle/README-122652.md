## Convenção escolhida

- **Tipo de identificador:** parâmetros de métodos e construtores.
- **Regra do Checkstyle:** `ParameterName`, propriedade `format`.
- **Padrão:** `^[a-z][a-zA-Z0-9]*$` (lowerCamelCase), de acordo com as *Oracle Java Naming Conventions* e o *Google Java Style Guide*. Aceita `numTiros`; rejeita `Num_Tiros`, `show_shots` ou `NumTiros`.
- **Gate:** action `dbelyaev/action-checkstyle@v4` (Checkstyle + reviewdog), com `level: error` e `fail_level: error`, para o workflow falhar quando houver violações. Com o `filter_mode` por omissão (`added`), só são reportadas violações nas linhas acrescentadas pelo pull request.

## O que o Checkstyle não consegue verificar

O Checkstyle só verifica a forma dos nomes, através de uma expressão regular: não sabe se um nome é significativo, pelo que `x`, `aux` ou `dados2` passam na regra tal como `numTiros`, e não deteta nomes enganadores (um parâmetro `linha` que guarda uma coluna) nem misturas de línguas (`naviosSunk`). Também não avalia a coerência entre nomes do mesmo conceito noutros pontos do código, nem se o nome está alinhado com o vocabulário do domínio do jogo. Por fim, a regra `ParameterName` não cobre os parâmetros de lambdas nem de blocos `catch`, que têm regras próprias (`LambdaParameterName`, `CatchParameterName`), e o modo `added` deixa passar violações já existentes no código, como os parâmetros `show_shots` e `show_legend` em `Game.java` e `IGame.java`.
