# Qodana quality gate: Long Parameter List (Aluno B)

## Tabela de mapeamento

| Cheiro (Fowler) | Inspeção no IDE | ID da inspeção | Métrica / limiar | Limitações |
|---|---|---|---|---|
| Long Parameter List | Method with too many parameters | `MethodWithTooManyParameters` | NOPM; opção `m_limit` (por omissão 5). Usado: `m_limit: 3` (4 ou mais parâmetros, igual ao perfil do MetricsTree: NOPM ≥ 4) | Limiar absoluto, não relativo ao sistema. Não reporta métodos que sobrepõem um método da superclasse. Não deteta *data clumps* nem sugere *Introduce Parameter Object*. |
| Long Parameter List (construtores) | Constructor with too many parameters | `ConstructorWithTooManyParameters` | `m_limit: 3` (por omissão 5) | Inspeção separada, mesmo limiar absoluto. |

## Reflexão

O Qodana apontou o método com 6 parâmetros introduzido no pull request e o gate falhou; ao reduzi-lo a 3 parâmetros, o gate passou. Como o limiar é absoluto (`m_limit: 3`), o resultado é muito sensível ao valor: com o valor por omissão (5) métodos com 4 parâmetros, como `Game.printBoard` ou o construtor de `Ship`, não seriam detetados. Pode haver falsos positivos, por exemplo construtores que legitimamente recebem vários valores, e falsos negativos, como métodos que sobrepõem métodos da superclasse. O livro de Lanza e Marinescu não define uma estratégia de deteção para este cheiro, por isso a abordagem fica limitada a contar parâmetros.
